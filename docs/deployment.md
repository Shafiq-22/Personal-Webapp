# The live deployment

This describes the instance running for the repository owner. Anyone else
cloning this project should follow [`setup.md`](./setup.md) instead.

## What is where

| Piece | Where |
| --- | --- |
| Database, auth, scheduled jobs | Supabase project `Cortex` (`ceadcrrxqtnpqgemtxvx`), region `ap-south-1` |
| Web app | Vercel project building `apps/web` from `main` |
| Scheduled work | `pg_cron` inside the Supabase project, calling edge functions |

## Why there is no environment configuration

The two values the browser needs - the Supabase URL and the anon key - are
committed in `apps/web/src/lib/public-config.ts`. That is not a shortcut around
secrets management: the anon key is a JWT that Supabase ships inside the
JavaScript bundle of every app that uses it, and it grants nothing on its own.
Row level security is the boundary, and every table has it.

An environment variable of the same name always wins, so moving these into
Vercel's settings later needs no code change.

The service role key is **not** committed and is not needed by the web app:

- scheduled work runs in Supabase Edge Functions, which receive the key from
  the platform
- public share pages call `resolve_share`, a security-definer function the anon
  role is granted
- the only feature that still wants it is writing Google OAuth tokens, and that
  path reports the missing key instead of failing

## How the scheduler authenticates

`pg_cron` runs inside Postgres and cannot hold the service role key. Instead:

1. `cron_tokens` holds a 64-character random token, generated by
   `gen_random_bytes` inside the database.
2. `invoke_edge_function` sends it as `x-cortex-cron`.
3. The edge function - which *does* hold the service role key, injected by
   Supabase - reads the expected token and compares it in constant time.

So the token never leaves the project, and rotating it is one `UPDATE`.

Because the functions authorise themselves this way, they are deployed with
`verify_jwt = false`.

## Scheduled jobs

| Job | Schedule | What it does |
| --- | --- | --- |
| `cortex-monitor-fetch` | `7 * * * *` | Polls sources that are due, stores new items, scores them |
| `cortex-digest-build` | `0 * * * *` | Builds the digest for anyone whose local delivery hour it is |
| `cortex-housekeeping` | `30 3 * * *` | Retires stale auto-topics, wakes snoozed items |

`cortex-calendar-sync` is deliberately **unscheduled**: Google OAuth is not
configured on this deployment, so the function has nothing to do. Re-schedule it
after connecting a calendar:

```sql
select cron.schedule('cortex-calendar-sync', '*/15 * * * *',
  $$select invoke_edge_function('google-calendar-sync')$$);
```

## Who can sign up

`signup_allowlist` contains one address. A signup from anything else is refused
by a trigger on `auth.users`. An empty table means open signups, which is how a
fresh clone behaves.

To let someone else in:

```sql
insert into signup_allowlist (email, note) values ('them@example.com', 'why');
```

## Checking on it

```sql
-- Did the last scheduled fetch work?
select id, status_code, left(content, 200), created
from net._http_response order by id desc limit 5;

-- Are any sources failing?
select name, last_status, last_error, last_fetched_at from sources order by last_fetched_at desc;

-- How much has arrived?
select count(*) from info_items;
```

## Redeploying

The web app redeploys on every push to `main`.

Edge functions do not - they are deployed explicitly:

```bash
./scripts/sync-edge-core.sh
supabase functions deploy monitor-fetch digest-build
```

## What is not set up

- **Google Calendar.** Needs an OAuth client, and `GOOGLE_CLIENT_ID` /
  `GOOGLE_CLIENT_SECRET` set on both Vercel and Supabase. Until then the
  calendar page works with tasks and time blocks but mirrors no events.
- **Push notifications.** They are delivered by the iOS companion, which needs
  a Mac to build.
- **On-device AI.** Same: it is the companion's whole purpose. The web app uses
  the deterministic planner and ranker and says so in the interface.
